# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Diwan** — a Tauri 2 point-of-sale app (desktop: Windows/macOS/Linux; plus Android and iOS), white-label by design: one codebase configured per client, with modules toggled on/off rather than forked. Read `docs/projectGoal.md` for the "why" and `docs/buildPlan.md` for the phase-by-phase "how" — every change should fit somewhere in that plan. `docs/` is **git-ignored** (kept beside the working copy, not published); it also holds `ADMIN_GUIDE.md`, `DEPLOYMENT.md`, `TESTING_CHECKLIST.md` (the manual QA pass) and `SUPPORT.md` (vendor-only).

All feature modules are implemented — Dashboard, Billing, Inventory (incl. CSV import, stock adjustments, stock take, barcode labels), Reports, Tables, Attendance, Expenses, Salary, Shifts, Employees, Users, Settings, Customers (pay-later/credit), Purchasing (suppliers, POs, GRN) and Ledger — plus refunds, KOT kitchen tokens, the first-run setup wizard, the vendor gate and licensing.

Stack:
- Frontend: React 19 + React Router 7, `zustand` for state, Tailwind CSS v4 (via `@tailwindcss/vite`), `lucide-react` icons, `recharts` charts, `jspdf` + `jspdf-autotable` for receipt/report PDFs.
- Backend: Rust with `rusqlite` (bundled SQLite) for local persistence, `chrono` for timestamps, exposed to the frontend as `#[tauri::command]`s.

## Commands

```bash
npm run tauri dev      # run the desktop app (spawns vite on :1420, then cargo)
npm run tauri build    # production bundle
npm run dev            # vite only, browser — `invoke()` calls will fail here
npm run build          # tsc --noEmit typecheck + vite build
npm run android:dev    # tauri android dev on a connected device
npm run android:build  # tauri android build --apk
```

Rust-only checks run from `src-tauri/`: `cargo check`, `cargo fmt`, `cargo clippy`, `cargo test` (single test: `cargo test core_modules_cannot_be_disabled`). One licence test is `#[ignore]`d because it needs a live server: `DIWAN_LICENSE_API_BASE=http://127.0.0.1:8099/api cargo test live_server -- --ignored` with `php -S 127.0.0.1:8099 router.php` running in the backend repo's `backend/public/`.

Frontend unit tests use Vitest: `npm test` runs them all (`vitest run`); a single file is `npx vitest run src/utils/format.test.ts`, a single test `npx vitest run -t "rounds each line"`. Tests sit next to the module as `*.test.ts` and cover pure logic only (money math, formatting, permissions) — there is no DOM/component test setup. There is no frontend linter; `npm run build`'s `tsc --noEmit` is the type safety net.

Releases: pushing a `v*` tag runs `.github/workflows/release.yml`, which builds every platform (Windows x64+x86, Linux x64, macOS arm64+x64, Android) onto one GitHub release. `src-tauri/gen/android` is generated and git-ignored, and `tauri android init` rewrites it — so release signing and printer permissions (Bluetooth/USB) are re-applied after init by `scripts/patch_android_signing.py` and `scripts/patch_android_manifest.py`. Put any Android manifest/Gradle change in those scripts, never in `gen/`. Run both locally after every `npm run tauri android init`. iOS is **not** in the release workflow (its header says so); it is built locally from `tauri.ios.conf.json`.

## Architecture notes

- **IPC boundary**: all SQLite access belongs in Rust. Add commands in `src-tauri/src/commands.rs`, register them in the `generate_handler![]` list in `lib.rs`, and expose them to the frontend as a function in `src/services/`. Arg names are camelCase on the JS side, snake_case in Rust.
- **Never call `invoke()` from a component.** `src/services/tauriClient.ts` is the only module that imports `@tauri-apps/api`; everything else goes through its `call()` helper, which wraps failures in `TauriCommandError`. A non-critical read that should degrade quietly catches at its call site (`.catch(() => fallback)`); a write never does — the cashier must see the failure.
- **Command naming**: `<module>_<action>` — `inventory_add_item`, `billing_create_sale`, `config_get_enabled_modules`.
- **Database handle**: a single `Db` (mutex-guarded `rusqlite::Connection`, WAL, foreign keys on) is opened in `lib.rs` `setup()` at `app_data_dir()/pos.db` and stored as managed state — take it in a command as `db: State<'_, Db>`.
- **Modules are dynamic and per-platform**: what a client sees comes from `enabled_modules` in SQLite, never from code. Each module has separate `desktop_enabled`/`android_enabled` and `desktop_locked`/`android_locked` columns; `Platform::current()` picks the column at compile time. `MODULE_CATALOGUE` in `db/schema.rs` (key, name, is_core, sort order, Android default) now covers Dashboard, Billing, Inventory, Reports, Tables, Attendance, Expenses, Salary, Shifts, Employees, Users and **Settings** — admin screens are catalogue rows too. `src/utils/navigation.ts` maps a `ModuleKey` to a route and icon (presentation only); labels and ordering come from the `modules` table. To add a module: add a constant to `db::modules::key`, a row to `MODULE_CATALOGUE` using it, a key to `ModuleKey`, an entry to `MODULE_NAV`, a `<ModuleRoute moduleKey=…>` in `App.tsx`, and a `require_module(&db, &[module_key::X])` in each of its commands (a read shared by several features passes all their keys; one being enabled is enough).
- **Two authorities toggle modules**: Owner/Admin via Settings (`modules::set_enabled`, which refuses a core module and anything locked), and the product-owner (vendor) account via `set_by_product_owner`, which sets enabled *and* locked and may disable anything, **billing included**. So nothing is guaranteed visible any more: when no enabled section is reachable the router lands on `/unavailable`.
- **`useModules()` is the frontend source of truth** for "what can the current user see?" — it intersects enabled modules with the role. The sidebar and the `ModuleRoute` guard both read it, so they cannot disagree. It is presentation: commands re-check with `require_module`.
- **Auth is enforced in Rust, mirrored in the frontend**: local accounts with argon2-hashed PINs (4–6 digits). `session.rs` holds the signed-in user (memory only; `auth_login`/`auth_logout` are the only writers) and every sensitive command calls `require_role` against it, never a role the JS side sends. `useAuthStore` is the UI mirror. Closing the app ends the shift. First run seeds an `Owner` account with PIN `1234` and the area PIN `db::schema::DEFAULT_AREA_PIN`. Until they're changed, `DefaultPinBanner` blocks Owner/Admin with a dialog that replaces them via `security_replace_default_pins` (which only ever overwrites a PIN still at its default).
- **Roles**: `src/utils/permissions.ts` holds the frontend rules and the full permission matrix in its doc comment; `commands.rs` (`require_role`, `caller_may_manage`, `assignable_roles`) enforces them. Owner/Admin see every enabled screen plus Settings and Users; Cashiers get Billing, read-only Inventory and table billing. There is exactly one Owner; it outranks Admin in user management and can never be deactivated. Role checks stack on top of module config, never replace it.
- **Sensitive-area PIN**: Reports, Attendance, Expenses, Salary and Employees are gated for *every* role by one installation-wide PIN (`db/security_pin.rs`), not by role. `AreaPinGate` asks for it on every visit and revokes the `AreaAccessSession` grant on unmount (a short timeout is the safety net); the commands behind those screens call `require_area_access`. `reports_get_sales_over_time` is shared with the Owner/Admin Dashboard, so it uses `require_admin_or_area_access`.
- **Vendor-only surfaces**: `vendor_gate.rs` stops a fresh install finishing setup without the vendor password — `config_update` refuses to set `onboarding_completed` without the grant, so the route guard is not the real check. The product-owner account opens through a hidden 7-tap trigger (`hooks/useSecretTapTrigger.ts` on the login store icon and the top-bar business name), uses its own idle-expiring `ProductOwnerSession`, and has no client-reachable reset. Keep all of these checks in Rust: IPC is reachable from devtools (`__TAURI_INTERNALS__` is always injected, even with `withGlobalTauri` off), so anything decided only in JS can be re-decided there.
- **Money is INTEGER minor units** (paisa/cents) in every column, suffixed `_minor`. Never floats — a till must not accumulate rounding drift. Convert only at the print/display boundary. Percentages (tax) stay REAL, but any amount derived from one is rounded straight back to whole minor units.
- **Migrations are additive-only**: `schema.sql` is all `CREATE ... IF NOT EXISTS` and is replayed on every launch, so it creates what is missing and rewrites nothing. `apply()` logs which tables were missing, verifies `EXPECTED_TABLES` afterwards, and bumps `PRAGMA user_version`. A change that must *modify* an existing table needs a numbered step guarded on `user_version` instead — never edit an existing `CREATE TABLE` in place once clients have data.
- **Historic data is immutable**: `sale_items.price_at_sale_minor` is copied at checkout, and deleting an item that appears on any sale is refused (`ON DELETE RESTRICT`) — retire it with `is_active = 0`.
- **Seeding must never clobber onboarding**: demo data only runs when the operational tables are empty, and it fills in config only where the client has not set a value.
- **Delete is soft where history exists**: `inventory_delete_item` hard-deletes an item that has never appeared on a sale; one that has is archived (`is_active = 0`) instead — the command returns `"deleted" | "archived"` so the UI can tell the cashier which happened. `inventory_get_items` excludes archived items unless `includeInactive` is passed.
- **Item add/edit is a full-row replace**, not a partial patch (`ItemInput` has every editable field required) — this is what lets clearing a category (or a photo) back to unset work unambiguously, unlike `AppConfigUpdate`'s `COALESCE`-based partial patch.
- **Product photos live on disk, never in SQLite**: `images.rs` writes each upload as its own file under `app_data_dir()/product-images/`, capped at `MAX_IMAGE_BYTES` (5 MB) on the way in, shrunk to `MAX_DIMENSION` (1024 px; JPEG unless see-through) and named by a hash of its content (`item-<hash>.jpg`, never the client's filename) — so the same photo has the same name on every counter of a business, and two products may share one file. `items.image_path` stores only that generated filename, not a path, so it survives a reinstall or an app-data-dir move. The frontend never sees raw bytes over IPC except once, on upload/read: `inventory_upload_image` takes base64 (the browser's `FileReader` already produced it, so no filesystem-access plugin/capability was needed) and returns the filename; `inventory_get_image` takes a filename and returns a `data:` URL ready for `<img src>`. `src/store/inventoryStore.ts` caches fetched data URLs by filename (`imageCache`/`ensureImage`) so a table of thumbnails fetches each image once.
- **A replaced or removed photo is deleted from disk** by the `inventory_update_item`/`inventory_delete_item` *commands* (not the `db::items` functions, which stay pure-SQLite) — they diff the old `image_path` against the new one after a successful write and call `delete_photo_if_unused` (no other item may still use the file). A photo is only removed when its item is truly deleted, never when archived (an archived item can still be looked up). A photo picked but never saved, or one replaced on another counter, is deleted a day later by `workspace::media::sweep` (hourly, in the sync loop, standalone too).
- **`items.image_path` was added after the table's first release**: `schema.sql`'s `CREATE TABLE IF NOT EXISTS` can't add a column to an already-existing table, so `db/schema.rs`'s `ADDED_COLUMNS` runs a guarded `ALTER TABLE ... ADD COLUMN` for it (and is the template for any future added-later column) — see the module doc comment for why this is still additive-only. `table_orders.cart_json` (below) was added the same way.
- **A sale is one SQLite transaction** (`Db::try_transaction`, via `commands::transact`, used by `billing_create_sale`): `db::sales::create_sale` re-prices every cart line against the live `items` row (never trusts a client-sent price), checks stock, inserts `sales` + `sale_items`, decrements stock, and — if a table was given — closes that table's parked order and frees it. A domain `Err` at any step rolls the transaction back — use `try_transaction`/`transact` for a domain function, never `with_transaction(|tx| Ok(domain_fn(tx)))`, which would commit whatever ran before the error; `db::sales::tests::insufficient_stock_rolls_back_the_whole_sale` proves this directly.
- **Refunds, tokens and shifts follow the sale's rules**: `db::refunds::create_refund` mirrors `create_sale` — one transaction, re-validated against live rows, its own ledger row (the original sale is never edited), stock put back. KOT tokens (`db/tokens.rs`) are printed *before* they are recorded (`commands::tokens_print` owns that order), so a printer failure never marks items as sent to the kitchen. Dine-in tokens diff per item against `table_order_id`; takeaway ("ad hoc") tokens have no order row and always print the full quantity. Each token goes to a kitchen `counter` (a separate concept from category). Shifts (`db/shifts.rs`, the `shifts` module) do cash-drawer reconciliation, and Billing's inline open/close-shift controls check that module flag directly. CSV import is deliberately *not* one transaction: each row is its own insert, and failures come back per row.
- **A sale's tenders live in `sale_payments`** (one row per method; `credit` = pay-later). `sales.payment_method` is the single method, or `split`/`credit`. Read the breakdown through the `sale_payment_lines` view (it falls back to one line of the whole total for sales with no rows), never `sales.payment_method` — shift reconciliation, the full report and the payment-type report all do. The view is created in `schema.rs` (not `schema.sql`) because `apply()` must drop it before any table rebuild. Tenders must add up to the server's total (`subtotal - discount + tax + service charge`; the delivery fee lives on the order, so the client sends tenders against `total - deliveryCharge`). `service_charge_minor` and the per-sale tax-exempt switch are client-computed and trusted like `taxMinor`.
- **Pay-later balances are derived, never stored** (`db/customers.rs`): outstanding = credit part − installments − refunds (refunds absorb unpaid credit first; `refund_cash_out` is what actually leaves the drawer). Credit needs a customer and a due date. Installments always name a sale — "on account" is spread oldest-due-first. Cash installments carry the receiver's `shift_id` and count in that drawer. Cashiers may use the `customers` module (take installments); archiving a customer, Purchasing and Ledger are Owner/Admin.
- **Stock outside selling goes through `stock_movements`** (`db/stock.rs`, `db/purchasing.rs`): goods received (GRN — also sets `items.cost_minor` to the received unit cost and advances its PO), manual add, damage, correction and stock-take variance, each a signed row written next to the `stock_qty` update. `sale_items.cost_at_sale_minor` snapshots cost for profit reports (`db/insights.rs`), which fall back to the live cost for older lines. Supplier balance = GRN totals − supplier payments.
- **Barcodes**: `stock_generate_barcodes` assigns in-store EAN-13s (`200` + item id + check digit); labels are a jsPDF built in `utils/barcodeLabelsPdf.ts` with the Code 128 encoder in `utils/code128.ts` (dynamically imported). Weight-scale labels (prefix + item code matched to `short_code` + weight/price + check digit, layout in Settings → Checkout) are decoded in Rust by `billing_lookup_scale_barcode`, tried when a 13-digit scan isn't an item's own barcode.
- **Reuse the shared building blocks** before hand-rolling markup or state: `components/ui/ModalCard.tsx` (`ModalCard`, `ModalHeader`, `Field`, `inputClass`), `ui/DataTable.tsx`, `ui/DateRangeInputs.tsx`, `hooks/useReport.ts` (load + reload + stale-response guard) and `utils/runAction.ts` for writes. Rust tests share fixtures in `db/test_support.rs` (`ring_up_with_line`, `backdate_sale` to a fixed day — never assert on "today", a run can cross midnight).
- **Billing search re-prices nothing** — `items::search_items` is read-only, ranks an exact barcode match first (so a scanner's Enter reliably adds "the top result"), and is a separate query from `inventory_get_items`/`list_items` (different ordering needs).
- **Dine-in tables (`tables` module)**: "Save to table" parks the cart as JSON on `table_orders.cart_json` (a deliberate Phase 4 stand-in for real draft line items — see `db/sales.rs`'s module doc; Phase 6, full Table Management, is expected to replace it) and marks the table `occupied`. Selecting an `occupied` table with a parked order shows "Load parked order" to resume it. Completing a sale with `table_id` set closes that table's open order (`status = 'billed'`) and frees the table (`status = 'free'`) inside the same transaction. `BillingPage` reads `tables` module enablement straight from `useModules().modules` (not `visibleModules`, which is role-filtered) and renders none of `TableSelector` when it's off — there is no "disabled" state to design for inside that component.
- **Money the client computes vs. the server re-derives**: `discountMinor` and `taxMinor` are computed client-side (`utils/billingTotals.ts`, mirroring the Rust seed data's `round(taxable * percent / 100)` formula) and sent as-is — trusted the same way `AppConfig.taxPercent` is. Only *price × qty* is re-derived server-side, because that is the one value with real tamper/staleness risk (a cart built minutes ago against a price that has since changed).
- **PDF is the real default receipt, not a placeholder**: `utils/receiptPdf.ts` (jsPDF + `jspdf-autotable`) builds an actual 80mm-thermal-shaped receipt and is dynamically `import()`-ed from `ReceiptModal` so its ~140KB chunk never loads on the billing screen itself. `printer/escpos.rs`'s `build_receipt_bytes` is complete and tested; The same bytes go out over a per-OS transport (see `printer/mod.rs`): on macOS/Linux `send_to_printer` (via `rusb`, `features = ["vendored"]` so libusb doesn't need to be preinstalled) auto-detects any USB device with a standard Printer-class (0x07) interface; on Windows `windows_spool.rs` goes through the Print Spooler by printer name, because raw USB fails once a driver is installed; on Android the install picks Bluetooth SPP or USB Host. Serial and network (TCP 9100) are still unimplemented. Always treat any error here as "fall back to PDF," never as a reason to fail a sale that's already committed.
- **Cart state is keyed by item id, not an array** (`useBillingStore.cart: Record<number, CartEntry>` + a separate `cartOrder: number[]` for row order): each `CartRow` subscribes to only `state.cart[itemId]`, so editing one line's quantity re-renders that row and the totals footer, not the rest of the cart. Search input/results live in local component state in `ItemSearchBar`, not the store, for the same reason in the other direction — typing there never touches cart state.
- **Licensing is asymmetric and verified in Rust, offline, on every launch** (`src-tauri/src/license/`). The licence server (`api/license-status.php` in the Diwan backend repo) signs `{v, kid, license_key, status, issued_at, expires_at, device_fingerprint, max_offline_days}` with an Ed25519 private key that exists only in the server's `.env`; the app embeds only public keys (`verify.rs`'s `ACCEPTED_PUBLIC_KEYS`, keyed by `kid` so a rotation ships a build accepting both before the server switches). `db/license.rs` stores the **signed bytes untouched** — never parsed fields — so editing the SQLite row just breaks the signature; every launch re-verifies then re-derives state (`state.rs::evaluate`). Launch never blocks on the network: `LicenseRuntime::load` in `setup()` is offline, and `runtime.rs` refreshes in the background (3s after launch, then 6-hourly) plus re-evaluates every minute so an expiry that lands mid-shift takes effect on time. Enforcement is `commands::require_license` on `billing_create_sale`, `refunds_create`, `tokens_print*`, and the false→true `onboarding_completed` transition — the frontend's `LicenseBanner`/`LicenseLockGate`/`LicenseSection` only render the `LicenseState` Rust emits (`license:changed` event → `licenseStore`). Reads are never gated so the owner can always see how to renew. Clock rollback is mitigated, not solved: local time below the payload's `issued_at` or below the stored high-water mark (10-min tolerance) → `ClockTampered`; more than `max_offline_days` since the last successful refresh → `CheckInRequired`; both clear on the next online refresh. A 403 on refresh clears the cache (the server disowned this key for this device); a 409 re-activates (support reset the binding for a device move). `client.rs`'s base URL is a const, overridable at build time via `DIWAN_LICENSE_API_BASE` and — debug builds only — at run time, so `DIWAN_LICENSE_API_BASE=http://127.0.0.1:8099/api npm run tauri dev` tests against a local `php -S` of the backend. TLS is reqwest `rustls-no-provider` + the `rustls` crate's `ring` provider, exactly like tauri's own `rustls-tls` feature — not reqwest's `rustls` feature, which drags in aws-lc-rs (cmake). On Android the client uses Mozilla's roots compiled in (`webpki-root-certs`, `client::with_bundled_roots`) rather than the OS verifier: rustls-platform-verifier's JNI/Kotlin/revocation path failed on real phones and every failure there read as "check the internet connection". `ring` needs a C compiler for Android; `cargo tauri android build` exports the NDK clang, a bare `cargo check --target aarch64-linux-android` does not.
- **Plans are signed entitlements, enforced in Rust** (`license/entitlements.rs`). Since the server's migration 016 the signed licence payload also carries `plan {code,name}`, `entitlements` (module keys plus the capabilities `inventory_advanced`, `reports_advanced`, `multi_user`, `mobile`) and `upgrade` (key → cheapest plan that has it). The runtime installs them from the verified payload whenever it loads or adopts one; `require_module` checks them before the module flag, and `require_capability` guards stock takes / CSV import / barcode generation, the advanced reports, `users_create` and non-Owner `auth_login`, and (in `require_license`) running on Android/iOS. `entitlements: None` — a licence issued before plans, or none — is unrestricted, so plans never take a module away from an existing customer. `config_get_enabled_modules` fills `entitled`/`requiredPlan` on each module: the nav shows plan-locked modules with a lock, `ModuleRoute` renders `UpgradeNotice`, and `useCapability` disables in-module buttons — all presentation. Keep the capability keys in step with `PlanCatalog::POS_KEYS` on the server. In tests the store is thread-local, so a test can install a plan without leaking into others. `LicenseState::Suspended` (server status `suspended`) locks billing like `Revoked` but is reversible.
- **One business, many counters** (`src-tauri/src/workspace/`, server side `Diwan\Workspace` + `docs/MULTI-COUNTER.md` in the backend repo). A counter connected in Settings → Business & counters keeps a *full* local copy of its business and syncs it (push then pull, every 5 s and after each write; `runtime::spawn_loop`), so every module and report keeps working — offline too — and is business-wide. Rules that keep this correct:
  - Every table in `workspace::spec::TABLES` gets a `gid` (`<install id>:<local id>`, set by an AFTER INSERT trigger) and change-capture triggers, installed by `workspace::local::install` at the end of `schema::apply` — after the table rebuilds, which drop triggers. **A new table must be added to `spec::TABLES` (and the server's `SyncEngine::ENTITIES`) or to the device-only list** — `every_operational_table_is_either_shared_or_deliberately_local` fails otherwise. **A future table rebuild must copy `gid`.** Foreign keys travel as gids (`codec`); a reference that is not a declared foreign key (like `stock_movements.reference_id`, ids inside `cart_json`) needs a hand translation in `codec.rs`.
  - Nothing local may decide stock: `items.stock_qty` never travels with the row; every change of it becomes a delta (trigger), and the local figure is central balance + unsent deltas (`local::recompute_stock`). Write stock as `stock_qty = stock_qty ± x`, never as an absolute value (the item form sends `originalStockQty` so an edit applies the typed difference).
  - `billing_create_sale` and `orders_pay` first take the cart's stock centrally (`runtime::reserve_for_sale`, 4 s timeout; no answer = record offline) and then record the sale inside `runtime::record_sale`, which tags its deltas with the reservation key; a failed write releases it (`abandon_sale`). Any new command that sells stock must do the same.
  - Downloaded changes are applied with `sync_state.applying = 1` so they are not echoed; first-run seeding (owner, demo data, platforms) is skipped on a connected counter. Shifts are cash drawers of *this* counter (`shifts::OPENED_HERE`); app_config splits into shared (`spec::CONFIG_COLUMNS`) and per-device columns.
  - Joining never merges: an empty business takes this counter's data (`upload`), otherwise this counter's data is replaced by the business's after a file backup, in one transaction (`download`). The server refuses pushes from a counter that has not done one of these.
  - An update queues the columns it changed and the cursor it was made at (`sync_outbox.fields/base`, filled by the `ws_<t>_upd` trigger, which skips no-op updates); `build_push` sends `fields`+`base` so the server replaces only those fields. An insert sends the whole row. A one-off resend of a single field (an upgrade, a re-sealed PIN) is an outbox row with `fields` set by hand — never a whole-row requeue, which would overwrite newer edits with a stale copy.
  - Photos and the logo are files beside the records (`media`): uploaded (only those the server lacks) before the push, downloaded after the pull, never sent through SQLite rows. `items.image_path` and `app_config.logo_path` are shared columns.
  - PIN hashes (`users.pin_hash`, `app_config.sensitive_area_pin_hash`) are sealed in `codec::read_row` and opened in `apply_row` (`pins`, key = HKDF of the licence key). A new protected column belongs in `pins::protected_columns`. The counter token is read and written only through `vault` (OS credential store where there is one; `sync_state.token` may hold just the `IN_VAULT` marker).
  - The loop polls every 2 s while busy, backing off to 30 s when quiet (`runtime::poll_interval`); desktop counters also nudge each other over UDP broadcast (`lan`, port 47291). `app_config.offline_sales = 'block'` makes `reserve_for_sale` refuse a sale it could not reserve.
  - Receipts and tokens of a business with several counters show the creating counter: `local::till_of` / `receipt_number` (`C2-12`), from `sync_terminals.seq`.
- **iOS rides on the Android paths with three exceptions**: `Platform::current()` maps iOS to the *Android* module columns (`db/modules.rs`), so a module's mobile config covers both. The exceptions: (1) there is no thermal-printer transport (`printer/escpos.rs` refuses → PDF fallback); (2) the licence fingerprint is a random id kept in the Keychain (`license/fingerprint.rs`, and renaming its service/account re-fingerprints every install); (3) licences are bought in-app (`iap.rs`). In that flow the server (`api/apple-iap-verify.php`) turns a StoreKit signed transaction into a normal licence key, activated via `LicenseRuntime::activate`, and the transaction is **finished only after activation succeeds**. Otherwise StoreKit re-delivers it and `spawn_unfinished_sweep` redeems it on the next launch. Every `iap::` function exists on all platforms (off iOS it returns `UNSUPPORTED`), so `commands.rs` needs no `cfg`. `PRODUCT_IDS` must match App Store Connect and the server's `APPLE_IAP_PRODUCTS`. Sign in with Apple is optional, and buying must never require it (App Review).
- **Navigation is platform-split once, in `AppLayout`**: desktop renders the attached, collapsible `layout/Sidebar.tsx` (pushes content; 240px expanded / 64px icon-only rail with `title` tooltips; `transition-[width]`), Android keeps the hamburger + `NavOverlay` drawer + `BottomTabBar`. Both containers render the same `hooks/useNavItems.ts` list (modules from `useModules()` ∩ role, then Employees/Users/Settings under their permission checks) so the platforms can't disagree about what a role sees — add a nav entry there, never in a container. `TopBar`'s hamburger, user chip and Sign out only render when `onOpenNav` is passed (Android); on desktop the sidebar footer owns identity + Log Out. The collapsed state persists as `app_config.sidebar_collapsed`, read with the theme in one `config_get_ui_prefs` call at boot by `store/uiPrefsStore.ts` (which also owns `theme`; there is no separate theme store).
- **Theming is semantic tokens, never raw palette shades** (`src/styles.css`): every colour utility in a component is one of `bg-bg/surface/surface-2/surface-3`, `text-fg/fg-2/fg-muted/fg-faint`, `border-line/line-strong`, `bg-accent`+`text-accent-ink` (fills), `text-accent-text` (green as text), `bg-accent-soft`, or a status trio (`danger|warning|success` × `-text/-soft/-line`, bare name = solid fill with `text-white`). They compile via `@theme inline` to `var(--t-*)`, whose values live on `:root[data-theme="dark"]` (the marketing site's exact hex) and `:root[data-theme="light"]`. Dark is the default: `index.html` ships `data-theme="dark"` statically; `store/uiPrefsStore.ts` reads `app_config.theme` at boot (before login, via `config_get_ui_prefs`) and sets the attribute. The toggle is the sun/moon in `TopBar` and Settings → Appearance; it writes through `config_set_theme` (any signed-in role — a display preference, not a business setting, hence not on the Owner/Admin `config_update` patch). Never write `bg-slate-*`, `text-white`-on-accent, or a `dark:` pair — the one sanctioned use of `dark:` (a `@custom-variant` on the attribute) is hue-categorical colours that must stay recognisably that hue in both themes (`utils/categoryColor.ts`, `UserTable` role badges). recharts can't read classes, so charts take colours from `hooks/useChartColors.ts`, which re-reads the `--t-*` vars on every theme change. Native `<select>`/number inputs are opted out of WebKit's light chrome in the base layer (each `<select>` carries `pr-8` for the CSS chevron). `receiptPdf.ts` is deliberately theme-independent (paper is white).
- **Permissions**: any Tauri plugin capability the frontend uses must be listed in `src-tauri/capabilities/default.json` or the call is denied at runtime.
- **Fixed dev port**: Vite is pinned to 1420 with `strictPort` because `tauri.conf.json` `devUrl` points there. Don't change one without the other.
- `withGlobalTauri` is off and the production CSP has no `'unsafe-inline'`; `devCsp` keeps `'unsafe-inline'` because Vite injects `<style>` tags for HMR. A library that injects `<style>` elements at runtime would need the CSP revisited. Nothing is fetched from the network for the UI: the Plus Jakarta Sans font is bundled (`@fontsource-variable`, imported in `main.tsx`; the splash uses its copy in `public/fonts/`).
- **Desktop splash** (`public/splashscreen.{html,css,js}`, the `splashscreen` window in `tauri.conf.json`) is plain files outside Vite, styled and scripted from same-origin files so the CSP needs no exceptions. `main` is built hidden and revealed by `commands::app_main_ready`, sent from `MainReadySignal`'s effect after React's first commit — not `requestAnimationFrame`, which WebKit pauses in a hidden window. The splash stays at least `MIN_SPLASH_MS` from its own first paint, and `MAX_SPLASH_MS` from launch is the fallback reveal. Its only permission is `core:app:allow-version` (`capabilities/splashscreen.json`). Keep the splash script inside a function scope: a top-level `const ipc` collides with the `window.ipc` global wry injects, and WebKit then rejects the whole script.
- Routing uses `HashRouter`: Tauri serves the bundle over a custom protocol in production, where a reload on a deep path would 404 under `BrowserRouter`.
- `productName`/window title are `Diwan` and the identifier is `com.diwan.pos`. The Cargo package is still named `tauri-app`, so the dev binary is `target/debug/tauri-app`.
